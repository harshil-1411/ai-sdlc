# IEC 62304 — medical device software lifecycle

> Scope: software that is, or is part of, a medical device. Safety classification drives
> how much of the standard applies. Source: drafted from public summaries of the
> standard. Owner: <name>. Last reviewed: <date>. **Not an authoritative interpretation.**

## Safety classification — establish this first

| Class | Definition | Effect |
| --- | --- | --- |
| A | No injury or damage to health is possible | Lightest process requirements |
| B | Non-serious injury is possible | Adds detailed design and integration testing |
| C | Death or serious injury is possible | Adds full architectural and unit verification |

Record the class in the compliance profile. Applying Class C process to Class A software
is expensive; applying Class A process to Class C software is a serious finding.

## Controls

| ID | Control | What to check in a change | Typical evidence |
| --- | --- | --- | --- |
| 62304-01 | Software development plan | The change is within a planned, documented lifecycle | Plan artifact |
| 62304-02 | Requirements | Software requirements are documented, verifiable, and traceable to system requirements | Requirement IDs in spec |
| 62304-03 | Architectural design (B, C) | Architecture identifies items and their interfaces, including segregation relied on for safety | Architecture diagram, spec section |
| 62304-04 | Detailed design (C) | Detailed design documented for each unit | Design section |
| 62304-05 | Unit verification (B, C) | Units verified against acceptance criteria | Unit test evidence |
| 62304-06 | Integration testing (B, C) | Integration and integration testing documented | Integration test evidence |
| 62304-07 | System testing | Software requirements verified at system level | System test evidence |
| 62304-08 | Release | Known residual anomalies documented and evaluated for risk | Release record, anomaly list |
| 62304-09 | Risk management | Contribution of software items to hazardous situations assessed; risk controls implemented and verified | Risk file linkage |
| 62304-10 | Configuration management | Items uniquely identified; changes controlled and traceable | Version control, change records |
| 62304-11 | Problem resolution | Problems recorded, investigated, and relevant parties notified | Defect and CAPA records |
| 62304-12 | SOUP | Software of unknown provenance identified, with title, version, and its requirements and known anomalies evaluated | Dependency inventory, SBOM |

## Blocking classes

Any **Not met** on 62304-02, 62304-09, 62304-10 or 62304-12. For Class C, also 62304-05.

## Common misses

- **SOUP inventory** left stale. Every dependency added is a SOUP entry with a version and
  an anomaly assessment, not just a line in a lockfile.
- Traceability from **system requirement to software requirement to test** broken at one
  link and nobody notices until an audit walks it.
- Residual anomalies known to the team but not documented in the release record.
- Safety-relevant segregation implemented but not identified as such in the architecture,
  so a later refactor removes it.
