# ISO 13485 — medical device quality management

> Scope: the quality management system around device software. Mostly process rather than
> code, but several clauses bite on how changes are made. Pair with IEC 62304 for the
> software lifecycle itself. Source: drafted from public descriptions. Owner: <name>.
> Last reviewed: <date>. **Not an authoritative interpretation.**

## Controls relevant to a change

| ID | Control | What to check in a change | Typical evidence |
| --- | --- | --- | --- |
| 13485-01 | Document control (4.2) | Controlled documents affected by the change are updated and approved | Document change record |
| 13485-02 | Design and development planning (7.3.2) | The change sits within a planned activity | Plan artifact |
| 13485-03 | Design inputs (7.3.3) | Requirements are complete, unambiguous, verifiable | Spec with requirement IDs |
| 13485-04 | Design outputs (7.3.4) | Outputs meet inputs and are reviewed before release | Review record |
| 13485-05 | Design review (7.3.5) | Reviews are recorded with participants and outcomes | PR approvals, review record |
| 13485-06 | Verification (7.3.6) | Outputs verified against inputs | Test evidence per requirement |
| 13485-07 | Validation (7.3.7) | The change is validated for intended use | Validation evidence |
| 13485-08 | Design transfer (7.3.8) | The change is correctly transferred to production/release | Release record |
| 13485-09 | Design changes (7.3.9) | Changes are reviewed, verified, validated and approved, with impact on product in the field assessed | Impact assessment |
| 13485-10 | Traceability (7.5.9) | Requirement to design to verification to release is traceable end to end | Traceability matrix |
| 13485-11 | CAPA (8.5.2/8.5.3) | Corrective and preventive actions are recorded and effectiveness verified | CAPA records |
| 13485-12 | Complaint handling and vigilance (8.2) | Field issues are assessed for reportability | Complaint records |

## Blocking classes

Any **Not met** on 13485-09 or 13485-10.

## Common misses

- **Impact on product already in the field** assessed for hardware changes and forgotten
  for software ones.
- Traceability held in a spreadsheet maintained by one person, which is a single point of
  failure and always out of date at audit.
- Design review recorded as "approved" with no record of what was actually reviewed —
  the exact failure mode this framework's PR artifact chain is designed to prevent.
