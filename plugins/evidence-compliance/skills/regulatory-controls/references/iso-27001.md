# ISO/IEC 27001:2022 — Annex A controls for software development and change

> Scope: the Annex A controls (2022 edition) that a software change can satisfy or break.
> Not covered: the ISMS clauses (4–10), risk assessment method, Statement of
> Applicability, and the many organisational, people and physical controls — those are
> managed by the ISMS, not by a diff. Check the organisation's Statement of Applicability
> first: a control excluded there is **N/A** with the SoA as evidence. Source: drafted
> from public descriptions of Annex A; control titles follow the 2022 edition.
> Owner: UNASSIGNED — the adopting organisation must assign a named owner before relying on this set (evidence doctor warns while unassigned).
> Last reviewed: never by an adopter; drafted 2026-09-24. **Not an authoritative interpretation.**

## Controls relevant to a code change

| ID | Control | What to check in a change | Typical evidence |
| --- | --- | --- | --- |
| ISO27001-A.5.8 | Information security in project management | The change's spec states its security requirements and risk tier; security is a planned activity, not a post-merge review | Spec security section, risk tier record |
| ISO27001-A.5.15 | Access control | New or changed endpoints, roles and data paths enforce access rules server-side, default-deny, least privilege | Authorisation tests, role matrix diff |
| ISO27001-A.5.23 | Information security for use of cloud services | Any new or changed cloud service is covered by the organisation's cloud-use process (approved service, configuration baseline, exit consideration) | Cloud service register entry, IaC diff |
| ISO27001-A.8.4 | Access to source code | Repository access is controlled; branch protection and required review are in force; no secrets committed | Branch protection config, secret-scan result |
| ISO27001-A.8.8 | Management of technical vulnerabilities | Dependencies and images scanned; findings triaged within the policy's timescales; no known-exploitable component introduced | Dependency/SCA scan report, triage record |
| ISO27001-A.8.9 | Configuration management | Security-relevant configuration is defined as code, versioned, reviewed, and drift is detectable | IaC / config file diff, baseline reference |
| ISO27001-A.8.15 | Logging | Security-relevant events are logged with actor, time and outcome; logs are protected from tampering; no sensitive data in logs | Log schema, log-content test, retention config |
| ISO27001-A.8.16 | Monitoring activities | New components and failure modes are covered by monitoring and alerting for anomalous behaviour | Alert/monitor definitions in the diff |
| ISO27001-A.8.24 | Use of cryptography | Algorithms, key lengths and key management follow the cryptography policy; no home-grown crypto; keys not in code | Crypto config, KMS reference, review note |
| ISO27001-A.8.25 | Secure development life cycle | The change followed the defined lifecycle: intent, spec, plan, review, test, approval | Artifact chain for the tracker key |
| ISO27001-A.8.26 | Application security requirements | Security requirements (authn, authz, input handling, data protection) are identified in the spec and each has a test | Spec requirement IDs mapped to tests |
| ISO27001-A.8.27 | Secure system architecture and engineering principles | The design applies the organisation's engineering principles (defence in depth, least privilege, secure defaults); trust boundaries identified | Spec design section, threat model |
| ISO27001-A.8.28 | Secure coding | Code follows secure coding standards; static analysis ran and findings resolved or justified | SAST report, review record |
| ISO27001-A.8.29 | Security testing in development and acceptance | Security tests exist for the changed behaviour and ran before acceptance; negative and abuse cases included | Security test results in CI, acceptance record |
| ISO27001-A.8.30 | Outsourced development | Code from contractors or third parties passes the same review, testing and acceptance gates as internal code | PR review record, supplier agreement reference |
| ISO27001-A.8.31 | Separation of development, test and production environments | The change does not collapse environment separation (shared credentials, prod data in test, dev access to prod) | Environment config, credential scoping |
| ISO27001-A.8.32 | Change management | The change is requested, assessed, authorised, tested and approved, and traceable end to end; author does not approve their own change | PR + tracker key + independent approval |
| ISO27001-A.8.33 | Test information | Test data is selected and protected; production personal or confidential data is not used in test without authorisation and masking | Test fixture review, masking config |

## Blocking classes

Any **Not met** on ISO27001-A.5.15, ISO27001-A.8.4, ISO27001-A.8.24, ISO27001-A.8.31,
ISO27001-A.8.32 or ISO27001-A.8.33. A Not met on ISO27001-A.8.8 blocks when the finding
is a known-exploitable vulnerability outside the policy's remediation window.

## Common misses

- **The Statement of Applicability is the scope.** Reviewing against a control the
  organisation excluded wastes effort; missing one it included is a nonconformity. Read
  the SoA before starting.
- **Evidence of operation.** Certification audits sample records over time. A control
  that exists in policy but leaves no dated artifact per change fails on sampling.
- Production data copied into test "just this once" (A.8.33), usually via a debugging
  script or a seeded fixture.
- Logging that captures the event but not the actor, or that logs tokens and personal
  data (A.8.15).
- Environment separation defeated by a shared service account or a CI job that can
  deploy to production from any branch (A.8.31).
